## 0. The decisions in one screen

| # | Decision | Why |
|---|---|---|
| 1 | Every profile keeps its current flat shape. Each profile's own settings move into **four subsections, all owned by the user**: `providers`, `ensemble`, `selection`, `high_quality_model`. | Static profiles need no migration. `providers` and `high_quality_model` already exist, so only `ensemble` and `selection` are new. |
| 2 | In a dynamic section (free, paid, local), llm-ext owns a **closed list of generated keys** and the user owns the four subsections. The writer replaces only generated keys, **one key at a time**, and never touches the YAML nodes of a user-owned subsection. That keeps their comments and key order. Any other key is refused. | This gives an exact boundary. Today the writer rewrites the whole section, so anything the user adds is lost (`pick.ts:1064` ✓). |
| 3 | A provider group is `{name?, api?, url?, api_key?, models?}`. Its identity is (resolved url, key reference). The profile's own `api`/`url`/`api_key` form group #0. Several groups may serve the **same** model id. They are tried in group order, and a group moves on to the next only on a key-scoped error (a certain credit error, from D4). A group with no `models:` list serves every model the profile does not bind to another group, which is how you add a second account at the same provider. | This covers "two keys, one model" and "next provider on insufficient credit" with no string-qualified id syntax. |
| 4 | The **qualified reference** is structural: the map `{provider: <group>, model: <id>}`. Reserved slots use it. A string form such as `group/model` is rejected. | `/` and `:` occur in real ids: every OpenRouter id, the `openrouter/free` pseudo-model (`index.ts:2427-2429` ✓), and `:free`. The `<binding>/<model>` idea in the comment at `config.ts:129-135` ✓ would collide with every OpenRouter id. |
| 5 | Reserved slots are `ensemble.reserved`: at most 2 entries, read ONLY by `getEnsembleModels`, and marked as manual. | This is USER 3.3. It replaces `ensemble_pins`, which has no reader (`benchmark/index.ts:1805` ✓). |
| 6 | Provenance is a per-profile set, `ResolvedProfile.manualModels`: every id that appears in a user-owned key. The send chokepoint skips the IRON RULE and the send-time price check for those ids. | USER: "Only auto-picked models" and "manual is manual". Where an id came from is a property of (profile, id), not of the call path. |
| 7 | Endpoint flavor (OpenAI-compatible or llama.cpp-native) is **detected at first use** and cached per base URL. There is no `type:` field. The known presets keep working by name. | USER 18:15. |
| 8 | The b.ai glm-5.3-flash slot is added by a one-time **seed step** with its own stamp. Once stamped it is never re-added, whatever the user deletes. | USER 18:15 "Default reserved slot". |
| 9 | Global settings stay global: `active`, `allow_paid_models`, `paid_benchmark_daily_cap_usd`. `ensemble_price_ceiling_usd_per_million` moves into `profiles.paid.selection`. | See section 1.3. |
| 10 | Migration is a list of named steps, each recorded in `dynamic-profiles-state.json` as it runs. Only llm-ext's own sections and its top-level key are rewritten, with one backup. Static profiles are never rewritten. Anything ambiguous is left in place, and validation then refuses it with the fix. | Fail fast at the validation layer, not by crashing. |

## 1. The schema

### 1.1 Annotated example (all four profile kinds)

```yaml
active: free                          # GLOBAL: which profile runs when no --profile is given
allow_paid_models: false              # GLOBAL: master paid-spend switch (applies to every profile)
paid_benchmark_daily_cap_usd: 0.5     # GLOBAL: daily wallet for llm-ext's own paid benchmark runs

profiles:
  # <-- do not touch, generated by llm-ext -->
  free:
    # ── generated: llm-ext rewrites these keys, one by one, on every update ──
    mode: remote-ensemble
    api: openrouter-remote            # group #0, named after its api: "openrouter-remote"
    api_key: $OPENROUTER_API_KEY
    free_only: true
    free_models:                      # the benchmarked ranking, best first = single-model fallback order
      - deepseek/deepseek-v4-flash:free
      - qwen/qwen3-coder:free
      - openai/gpt-oss-120b:free
    model: deepseek/deepseek-v4-flash:free      # display copies of free_models[0..2] (ignored under free_only)
    second_model: qwen/qwen3-coder:free
    third_model: openai/gpt-oss-120b:free
    tool_models: { security_scan: deepseek/deepseek-v4-flash:free }
    # ── yours: every regeneration keeps these exactly as written (bytes and comments) ──
    providers:
      - name: bai                     # seeded once when $BAI_API_KEY is set; yours to edit or delete
        api: chat-b-ai-remote         # known preset: url, default key var, "bills nothing"
        api_key: $BAI_API_KEY
        models: [glm-5.3-flash]
    ensemble:
      reserved:                       # at most 2; ensemble commands only; never benchmarked, price-gated or queued
        - provider: bai
          model: glm-5.3-flash        # the 3rd member (2nd here) comes from free_models, in rank order

  # <-- do not touch, generated by llm-ext -->
  paid:
    mode: remote-ensemble
    api: openrouter-remote
    api_key: $OPENROUTER_API_KEY
    model: z-ai/glm-5.2
    second_model: moonshotai/kimi-k2.6
    third_model: deepseek/deepseek-v4
    paid_models: [z-ai/glm-5.2, moonshotai/kimi-k2.6, deepseek/deepseek-v4, qwen/qwen3.6-plus]
    tool_models: { mass_scout: qwen/qwen3.6-plus }
    # ── yours ──
    selection:
      price_ceiling_usd_per_million: 1.3   # auto-picked models only: input AND output each <= this
    providers:
      - name: or-backup                    # 2nd OpenRouter account. No `models:` = alternate for every model
        api: openrouter-remote             # not bound to another group; tried after group #0 on a certain
        api_key: $OPENROUTER_API_KEY_2     # insufficient-credit error (each key's credit is checked separately)
    ensemble:
      reserved:
        - model: anthropic/claude-sonnet-5 # no `provider:` = every group that serves it, in group order
                                           # (openrouter-remote, then or-backup). Manual: no benchmark, no ceiling.
    high_quality_model: { id: z-ai/glm-5.2, reasoning_effort: max }

  # <-- do not touch, generated by llm-ext -->
  local:
    mode: local
    api: llamacpp-local
    model: qwen3-coder-30b
    free_models: [qwen3-coder-30b, gemma-4-26b]   # ranked (D7: pass, context, tok/s); single-model fallback order
    detected_providers:                          # generated: what the local probe found (was `providers` before 14.1)
      - name: llamacpp-local
        api: llamacpp-local
        url: http://localhost:8080
        models: [qwen3-coder-30b]
      - name: ollama-local
        api: ollama-local
        url: http://localhost:11434
        models: [gemma-4-26b]
    # ── yours ──
    providers:
      - name: lan-box                   # no `api:` means `name` and `url` are required;
        url: http://192.168.1.20:8080   # the protocol is detected at first use
        models: [llama-4-scout]
    ensemble:
      reserved:
        - provider: lan-box
          model: llama-4-scout

  my-mix:                               # STATIC: used exactly as written, never rewritten, never benchmarked
    mode: remote                        # remote-ensemble would fan ensemble commands out to the 3 models
    api: openrouter-remote              # group #0 = "openrouter-remote"
    api_key: $OPENROUTER_API_KEY
    model: z-ai/glm-5.2                 # single-model fallback order: 1st
    second_model: glm-5.3-flash         # 2nd, served by bai, then bai-2 (group order)
    third_model: moonshotai/kimi-k2.6   # 3rd
    providers:                          # same subsection as in the dynamic profiles
      - name: bai
        api: chat-b-ai-remote
        api_key: $BAI_API_KEY
        models: [glm-5.3-flash]
      - name: bai-2                     # 2nd b.ai account, same model, its own credit
        api: chat-b-ai-remote
        api_key: $BAI_API_KEY_2
        models: [glm-5.3-flash]
      - name: or-backup                 # alternate OpenRouter account for every unbound model
        api: openrouter-remote
        api_key: $OPENROUTER_API_KEY_2
    high_quality_model: { id: z-ai/glm-5.2 }
    # `ensemble:` and `selection:` are REFUSED here: the ensemble of a static profile is
    # model/second_model/third_model, and nothing in a static profile is auto-picked.
```

The walk for `my-mix` on a single-model command, once D4 adds the credit rule:

1. glm-5.2 on `openrouter-remote`. A certain credit error marks that group dead for the rest of the walk.
2. glm-5.2 on `or-backup`.
3. glm-5.3-flash on `bai`. On a credit error, glm-5.3-flash on `bai-2`.
4. kimi-k2.6: `openrouter-remote` is skipped without a request, because it is dead; `or-backup` is tried.

The listed order is kept, and each key is judged independently.

### 1.2 Subsections: names and why

| Subsection | Allowed in | Contents | Why this name and placement |
|---|---|---|---|
| `providers` | every profile | ordered provider groups | Already the key for bindings (`config.ts:136` ✓). Keeping it means existing static profiles stay valid. |
| `ensemble` | free, paid, local | `reserved:` (a list of at most 2 `{provider?, model}`) | A map, not a bare list, so later ensemble settings have a home without another top-level key. A static profile's ensemble is its three model fields, so it is refused there. |
| `selection` | free, paid, local | paid: `price_ceiling_usd_per_million`; free and local: none yet (an empty map is allowed) | "How llm-ext auto-picks this profile's models." Refused on a static profile, where nothing is auto-picked. |
| `high_quality_model` | every profile | unchanged (`config.ts:323-349` ✓) | Already a subsection. Today it cannot be set on `paid`, because the child's full rewrite wipes it. It becomes user-owned there at no cost. |
| `detected_providers` | local only (generated) | local's probe output, same shape as `providers` | Local's generated routes must not share a key with the user's groups. Otherwise the ownership boundary differs per profile, and the writer would have to merge inside one list. |

Not made user-owned, to keep this change minimal: `timeout`, `context_window`, `app_name`, `http_referer` on dynamic
profiles. Today they are wiped by the child's rewrite; from 14.1.0 they are refused by the closed-key check. Add one
to `DYNAMIC_USER_OWNED_KEYS` when a user asks for it.

### 1.3 What stays global, and why

| Key | Stays global because |
|---|---|
| `active` | It chooses between profiles, so it cannot live inside one (`config.ts:201`, `effectiveProfileName` `:892` ✓). |
| `allow_paid_models` | The USER master spend switch. It forces every remote profile to free (`shouldForceFreeMode` `config.ts:2974-2979` ✓). A per-profile copy would defeat "one switch governs every kind of paid spend" (`config.ts:210-219` ✓). |
| `paid_benchmark_daily_cap_usd` | A wallet guard over the machine-wide daily-spend ledger that paid benchmark runs book into (`benchmark/index.ts:1956-1975` ✓). It belongs with the spend switch. Moving it into `paid.selection` would be defensible (only the paid maintainer's spawn is pre-capped), but it would cost a migration step and give the user nothing. |
| ~~`ensemble_price_ceiling_usd_per_million`~~ | **Moves** to `profiles.paid.selection.price_ceiling_usd_per_million`. Every reader serves `paid` only: `dynamic-maintainer.ts:826,859` ✓, `profile-detector.ts:245` ✓, `benchmark/index.ts:1988` ✓. |

`getEnsemblePriceCeiling(settings)` (`config.ts:956` ✓) **keeps its signature**. Only its body changes, to read
`settings.profiles.paid?.selection?.price_ceiling_usd_per_million`. D3a's new predicate and all three callers are
therefore untouched.

## 2. Resolution rules

### 2.1 `resolveProfile(name, profile)` (`config.ts:2502-2594` ✓)

- **Groups.** `resolveGroups(profile)` returns `ResolvedRoute[]` in order: group #0 (from the profile-level
  `api`/`url`/`api_key`/`api_token`, with `primary: true`), then `providers[]`, then `detected_providers[]` (local
  only).
  - `ResolvedRoute` (`config.ts:89-108` ✓) gains `name`, `keyRef` and `primary`.
  - `keyRef` is the env-var name for `$VAR`, `sha256:<12 hex>` for a literal key, or `none` for an unauthenticated
    local endpoint. It never holds the secret, following the `credentialFingerprint` precedent
    (`free-rotation.ts:848` ✓).
  - Names: an explicit `name` wins. Otherwise the name is derived from `api`. Derivation walks the groups in order
    and adds `-2`, `-3` to repeats. Group #0 is always named after its `api` and cannot be renamed. A group with no
    `api` must carry an explicit `name`.
- **Serving groups.** `routesFor(id): ResolvedRoute[]` returns the groups whose `models` lists `id`, in group
  order. If no group lists it, it returns the catch-all groups: #0 plus every group without `models:`, in order.
  It replaces `routeByModel` (first binding wins, `config.ts:2492` ✓).
  - A thin `routeForModel(id)` = `routesFor(id)[0]` stays for callers that only need billability or the first
    route: the free rotation pool, the subsystem spend sites and the queue pruning.
  - Billability of an id becomes "ANY serving group is billable". That fails closed. It is used by
    `getActiveBillableForModel` (`config.ts:2954` ✓) and by the free_only exemption (`config.ts:1649-1655` ✓).
- **`reservedSlots`**: `{modelId, routes}[]` from `ensemble.reserved`. `routes` is the named group, or
  `routesFor(model)` when `provider` is omitted.
- **`manualModels: ReadonlySet<string>`** (provenance, requirement 8):
  - STATIC profile: `chainModelIds(name, profile)` (`config.ts:1460-1513` ✓). That already means `model`,
    `second_model`, `third_model`, `free_models`, `paid_models`, `tool_models` values and an explicit
    `high_quality_model.id`, under the right conditions.
  - DYNAMIC profile: the reserved-slot ids plus an explicit `high_quality_model.id`.
  - The default high-quality id (`HIGH_QUALITY_MODEL_DEFAULTS`) is never manual, because llm-ext picked it.
- The price ceiling is not a resolved field. It is read through `getEnsemblePriceCeiling` as above.
- `freeModels`/`paidModels`/`model`/`second`/`third` are unchanged. D3b owns the static free_only change.

### 2.2 `profileChain(profile, tool)` (`profile-fallback.ts:127-157` ✓): single-model commands

- The id list is unchanged: head, then pool for a dynamic profile; the written list for a static one (D3b).
  **Reserved slots are never read here** (USER: ignored outside ensemble commands).
- Each id expands to one entry per serving group, **model-major**: `(id1,g1) (id1,g2) (id2,g1) …`. The listed order
  is therefore kept, and group order breaks ties. `ChainEntry` gains `route`.
- Skip state for one walk:
  - `deadBaseUrls`: `"endpoint"`, as today.
  - `deadGroups` keyed by `url + keyRef`: the new `"credit"` kind, from D4. It moves to the SAME id's next group.
  - After a `"model"` failure the id's remaining groups are skipped. A 404, a 400 or a 5xx on one key would repeat
    on a second key of the same provider.
- `walkProfileChainOnce` (`index.ts:2683-2715` ✓) passes `route: entry.route` in the completion options.
- `resolveConnection` (`provider/connection.ts:44` ✓) uses `options.route ?? deps.routeForModel(model)`.
  - A `primary` route takes today's backend path: LM Studio probe and `apiHeaders()`.
  - Any other route takes the routed path (`:95-103` ✓).
  - `SimpleCompletionOptions` (`provider/completion.ts:341` ✓) gains `route?`. `resolveConnection` has exactly two
    call sites (`completion.ts:378, 608` ✓).

### 2.3 `getEnsembleModels()` (`index.ts:3427-3511` ✓): ensemble commands

1. `members = reservedSlots` (in written order; at most 2).
2. The remaining `3 - members.length` come from the profile's ranking, excluding reserved ids:
   - free mode: `selectFreeEnsembleModels(activeFreePool(), …)` (`:3452` ✓);
   - dynamic paid: the slot-substitution block (`:3482-3496` ✓);
   - static: exactly model/second/third. A static profile cannot carry `ensemble:`.
3. Reserved members:
   - skip `selectFreeEnsembleModels` filtering, `isUnusable` substitution and free-rotation replacement. They are
     mandatory, so a failure surfaces as that member's error result;
   - may fall back across their own `routes` on a certain credit error (D4);
   - are still subject to the free-mode cost check (`:3465-3472` ✓). A paid reserved id under free mode is refused.
4. The return shape gains `route?` per member. The fan-out call (`:3082-3091` ✓) passes it.
5. The ensemble gates stay as they are: `mode === "remote-ensemble"` (`:3432` ✓) and `backend.type === "openrouter"`
   (`:3004-3008` ✓). **Coordinator decision (D-L), see section 6:** `local`'s generated mode is `local`, so a local
   reserved slot is inert until those two gates admit it.

### 2.4 The send chokepoint (`provider/connection.ts`)

```text
billable       = !route.isLocal && !route.isFreeProvider        (unchanged, :59-61)
assertFreeOnlyModel(...)                                        (unchanged, all origins, :62-67)
if (toolCtx && !deps.isManualModel(model)) assertModelValidated(model, toolCtx, billable)   (:75-76 today)
D3c send-time price check: same `!deps.isManualModel(model)` guard
```

`ProviderDeps` (`provider/types.ts:96-121` ✓) gains `isManualModel(model)`. index.ts wires it as
`activeResolved?.manualModels.has(model) ?? false`, next to `routeForModel` (`index.ts:1643` ✓).

**Why a set and not a flag threaded through each call:** the exemption rule is "the user vouched for this id in this
profile". An id that is both reserved and in the auto ranking is exempt on both paths. That is harmless: the ranking
only admits ids that passed the gate (D3c), and the paid ranking only admits ids under the ceiling.

This replaces the audit's suggested `isDynamic` flag (conformance audit 3.1 (a)). It should be handed to
D3b, the first slice that exempts anything.

## 3. Regeneration and preservation (the ownership boundary)

### 3.1 Key tables (`config.ts`, next to `DYNAMIC_PROFILE_NAMES` `:842` ✓)

| Profile | GENERATED (llm-ext rewrites) | USER-OWNED (preserved exactly) |
|---|---|---|
| free | mode, api, url, api_key, free_only, free_models, model, second_model, third_model, tool_models | providers, ensemble, selection, high_quality_model |
| paid | mode, api, url, api_key, model, second_model, third_model, paid_models, tool_models | same four |
| local | mode, api, url, api_token, model, free_models, detected_providers | same four |

The tables are staged by slice (section 5): D0 ships `selection` and `high_quality_model`; D6a adds `providers` for
paid and local, with local's rename; D5 adds `ensemble` everywhere, plus `providers` for free once the b.ai binding
stops being generated.

### 3.2 Rules

1. **Closed key set.** A dynamic section may hold only GENERATED ∪ USER-OWNED keys. `validateProfile` refuses any
   other key when `isDynamicProfileName(name)` (error E-D1).
   - This is what makes the allowlist safe: a misspelt `ensembel:` is refused instead of being silently dropped by
     the next regeneration.
   - Static profiles keep ignoring unknown keys, as today. They refuse only the removed keys and the dynamic-only
     subsections.
2. **One writer for generated keys.** `writeDynamicProfileSection` (`pick.ts:995-1112` ✓) keeps its signature and
   its lock. `patch` still receives the full current section, user keys included, so candidate validation sees the
   reserved slots and groups. Behaviour changes in four places:
   - it takes **only GENERATED keys** from `next`. Every other key in `next` is ignored. So neither the child's
     full-replacement `() => next` (`benchmark/index.ts:1601, 1836, 2037` ✓) nor the maintainer's
     `applyPatch(currentSection, …)` (`dynamic-maintainer.ts:565-567` ✓) can overwrite a user key;
   - it writes each generated key with `setIn(["profiles", name, key], v)`, and `deleteIn` for a generated key that
     is missing from `next`. This replaces the whole-section `setIn` at `:1064`. User-owned YAML nodes are never
     replaced, so their comments and order survive;
   - the no-op comparison (`:1038` ✓) compares the generated projection only;
   - marker handling and the backup of an unmarked section are unchanged.
3. **One writer for user keys:** `writeDynamicUserKeys(settingsPath, name, mutate)`, under the same
   `settings.write.lock`. Only the one-time migration and seed steps may call it. Nothing that runs on every update
   writes a user-owned key.
4. **Regeneration of an invalid marked section** (`dynamic-maintainer.ts:332-443` ✓):
   - first validate the user-owned subsections alone, with `validateUserOwnedKeys`;
   - if they are invalid, log the user's error and skip. **Never regenerate**, because it is their data;
   - otherwise regenerate the generated keys only. The writer does that by construction.
   - Also fix the `name === "free" ? unpopulatedFreeProfile() : unpopulatedPaidProfile()` choice at `:371` ✓: use
     `unpopulatedDefaultProfile(name)`.
5. **Unmarked hand-written section:** unchanged. The one-time P6c-a adoption or backup-and-regenerate stays
   (`pick.ts:1240-1402` ✓), and the refusal after that stays (`config.ts:2161-2164` ✓). Only the text of
   `reservedDynamicProfileNameError` (`:874-880` ✓) changes, to name the new option: "keep the marker line and add
   `providers`/`ensemble`/`selection`/`high_quality_model` inside the generated section; to hand-pick every model,
   use a profile with another name."
6. **b.ai seeding (once, ever):**
   - the step `bai-reserved-seed` runs at boot when three things hold: the step is not yet recorded, `$BAI_API_KEY`
     resolves, and `profiles.free` exists;
   - it adds the group `{name: bai, api: chat-b-ai-remote, api_key: $BAI_API_KEY, models: [glm-5.3-flash]}`. It
     reuses an existing group named `bai` if that group has the same preset; a `bai` group with a different preset
     skips the seed with a notice;
   - it adds `ensemble.reserved: [{provider: bai, model: glm-5.3-flash}]` when there is room and no slot already
     names glm-5.3-flash;
   - it then records the step.
   - After that it never runs again. Deleting the slot, the group, or the whole `free` section does not bring it
     back.
   - If the key is not set, nothing is recorded, so the slot appears on the first boot after the user exports
     `$BAI_API_KEY`.
7. **Banner** (`renderDefaultSettingsYaml`, `config.ts:1226-1236` ✓): replace "do not hand-edit them" with the
   ownership rule. Add a static-profile-with-groups example to the trailing template (`:1284-1309` ✓).

## 5. Migration (one-time, stamped per step, fail fast)

- **Where:** a new `migrateSettingsTo141(settingsPath, opts)` in `benchmark/pick.ts`, next to
  `migrateProfileSections`. It runs at boot right after that call (`index.ts:394` ✓), so it only ever sees MARKED
  dynamic sections. It follows the same never-throw contract.
- **Stamp:** `DynamicProfilesState.migrationsApplied?: string[]`.
  - **Trap:** `readDynamicProfilesState` rebuilds the object field by field and drops unknown fields
    (`default-profiles-state.ts:229-238` ✓). The new field must be carried through there, or the next state write
    erases it and every step runs again.
  - Recording each step separately (instead of one `migratedAt`) matters because the steps land in different slices.
    A dev build that runs D0's steps must not mark D5's steps done.
- **Backup:** one `backupSettingsFile(path, "settings-before-14.1", "migration")` before the first step that
  rewrites anything (`pick.ts:929` ✓).
- **Ambiguous** means: leave the document as it is, do not record the step, print nothing. The validation errors in
  section 4 then refuse the command with the fix. No legacy reader survives: after 14.1.0 the old keys are only
  *detected*, to refuse them.
