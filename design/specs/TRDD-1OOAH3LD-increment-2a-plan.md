## Rationale
For a local profile that explicitly opts in, llm-ext starts llama-server itself when a command first calls the model, recognises its own server, never touches another process, and gives the user server-status and server-stop.

## Design
- Opt-in key `server: managed` on local profiles (PROFILE_TYPE_FIELDS.local, same five touch points as request_options). Valid only with api llamacpp-local and url http://127.0.0.1:<explicit port>; every platform (see Revision 4); win32 live verification is deferred to 2d. Profiles without it are unchanged.
- Target computed at call time from activeResolved through providerDeps (index.ts ~1765): model `org/repo:quant` (kind hf) or an absolute .gguf path with no whitespace that exists (kind file).
- New module scripts/llm-ext/src/local-llama-server.ts. Config-dir files: state llama-server-<port>.json {pid, model, port, ctx, startedAt} written temp-then-rename, mode 0600; log llama-server-<port>.log (previous kept as .log.1 on each spawn); lock dir llama-server-<port>.lock.
- New ASYNC mkdir lock (mkdir to take, rmdir in finally, same stale rule as mkdir-lock.ts). Inside the lock: re-read state; identity = kill(pid,0) (EPERM = not ours) plus `ps -ww -o command= -p <pid>` tokenised (darwin; per platform see Revision 4) (argv0 basename llama-server, exact token after -hf/-m equals model, exact token after --port equals port). Our server with same model and ctx: no spawn. Different model or ctx: refusal telling the user to run `llm-ext models server-stop`. No valid state: TCP-connect probe; a listener = hard failure naming the port (and the stale state file if present). Port closed: spawn `llama-server (-hf <model> | -m <path>) --alias <model> --host 127.0.0.1 --port <port> [-c <ctx> when > 0] --jinja <IDLE FLAGS>` detached, env process.env, stdio to the log, ENOENT error says llama-server is not on PATH, unref, state written with the child pid before the lock is released.
- Readiness outside the lock, every 0.5 s: pid dead = failure with log hints; TCP refused with pid alive = downloading or starting (the port stays closed for the whole download, measured); 503 = loading; 200 = GET /v1/models data[0].id must equal the model, else hard failure naming both values. Stall limit: failure when neither the log nor the model cache folder (llama.cpp order LLAMA_CACHE, HF_HUB_CACHE, HUGGINGFACE_HUB_CACHE, HF_HOME/hub, XDG_CACHE_HOME/huggingface/hub, ~/.cache/huggingface/hub; partial file blobs/<sha>.downloadInProgress, measured) has grown for 120 s. The wait is not bounded by the request timeout.
- Hints: unknown model architecture or load error: on darwin with brew `brew upgrade --fetch-HEAD llama.cpp`, else upgrade llama.cpp; couldn't bind: port conflict; else last 20 log lines.
- In-process: one in-flight promise per port. A failed start is remembered per port for the rest of this process (this command), so later requests fail fast without spawning; it is never written to disk, so the next command tries again. After a success, each call re-checks kill(pid,0), and a dead pid re-runs the full path (a server stopped from another shell is restarted by the next request). A supervisor failure follows the user's default, fallback on errors (Revision 4).
- Hook: provider/connection.ts resolveConnection calls optional deps.ensureLocalServer() in the primary openai_api branch before detectEndpointFlavor (:184). Measured: the judge and mass-scouting target OpenRouter only; the local benchmarks send to services the local scan found running, which can include the managed server once it is up (they never start it).
- Commands (core tools, no LLM request): `llm-ext models server-status` (llama_server_status: every llama-server-*.json, port, model, pid, ours and alive, /health code, RSS, last log line) and `llm-ext models server-stop [--port N]` (llama_server_stop: identity check, SIGTERM, 10 s, SIGKILL on POSIX; Windows ends the process at once (see Revision 4), remove state; never by port; reports stale state). Touch points: cli/launcher.ts FIXED_GROUPS.models, tools/definitions.ts catalog and profile-type row, index.ts dispatch, RECONCILE_SKIP_TOOLS, CLI_TOOLS_WITHOUT_RESOLVED_PROFILE, index.test.ts expected list, README counts and names, docs/agent-usage-reference.md, docs/tool-use-cases.md, skills/llm-externalizer-cli-reference/SKILL.md.
- Stated consequences: a context_window or model change refuses until server-stop (increment 4 must own the calibrated restart); with no context_window LFM3 uses 262144 tokens, about 4.8 GB awake; servers started under another LLM_EXT_CONFIG_DIR are foreign; whether a background auto-bench in another process (it uses the normal request path, unlike local-bench.ts which only targets services the scan found running) can start the server is unverified; the implementing worker must check and state it. Until 2c lands, the 2a server has no API key, the web UI is on and CORS allows all origins, so any web page open in the browser can send requests to the model on 127.0.0.1:<port>. Increment 5 must write url http://127.0.0.1:8181 (the llamacpp-local preset default is localhost).
- Tests (real, no mocks): pure tests for validation, argv tokenising (--port 818 is not 8181), state round-trip, identity against a live `sleep` process; integration with real llama-server and ggml-org/tiny-llamas:Q4_0 (19 MB) in a persistent /tmp LLAMA_CACHE (lasts until reboot), random free port, checks only /health and /v1/models (n_ctx_train 128, no chat template): cold start, reuse in one and two processes, forced concurrent start, foreign refusal, mismatch refusal, status, stop, restart after kill.

## Review-born decisions (user rulings 2026-10-28)
- The opt-in key itself and its name `server: managed` (review suggested a more specific name such as `managed_server` to avoid later collisions; not yet decided). (APPROVED)
- A context_window or model change refuses until `llm-ext models server-stop` instead of restarting (affects how increment 4 applies calibrated values). (APPROVED)
- A server stopped from another shell is restarted automatically by the next request. (APPROVED)
- win32 is refused (the supervisor is POSIX-only). (WITHDRAWN by the user: the server must run on every platform)
- The forced concurrent-start test is only as strong as the async lock (no fail-open in the new lock).
- Shipping 2a before 2c, that is, a server with no API key, the web UI on and CORS open to all origins, until 2c lands. (APPROVED)

## Revision 4 (2026-10-28, after review rounds on rev 3 and rev 4; waiting for user approval)

Evidence: reports/llama-cpp-profile/20261028_193341+0100-2a-rev4-measure.md (MEASURE), rev-3 and rev-4 adversarial reviews.

- Pieces: 2a-core (managed server, built-in sleep, opt-in, lock, identity, mismatch refusal, auto-restart, download-aware readiness, server-status and server-stop, spawn on every platform) and 2e (kill after 2 hours without requests, watcher process, setting capped at 120 minutes) are separate commits but ship in the SAME release: no publish may contain 2a-core without 2e, because the user ruled "sleep, but with a timeout (max 2 hours inactive, beyond that is killed)". 2e idle clock counts only llm-ext's own requests plus the server request counters, never the log mtime (the server's own sleep line touches it); each watcher is bound to its server pid and exits when that pid is gone or replaced.
- 2d: the llm-ext command that installs and configures llama.cpp when missing, plus live Windows verification. 2b disk check and 2c one symbolic API key for every local service: unchanged.
- --stop_on_errors moves to its own new TRDD (cited by TRDD-1OOAH3LD and TRDD-ZGSGGHQG), minted as its own commit. Acceptance rule carried there: a request waiting in llm-ext's memory queue, held by Locals, or queued by llama-server for a free slot is never an error.
- Failure under the user's default (fallback on errors): a supervisor failure throws ManagedServerError, marked with attachFailure(err, {final: "stop"}) (http.ts:553) so chatCompletionWithRetry (completion.ts:1367) neither retries it nor counts it toward the circuit breaker; chatCompletionSimple calls resolveConnection on every attempt (completion.ts:511, :768), so without the mark one entry would run the start-up path up to 4 times. walkProfileChainOnce (index.ts:3247) gets an instanceof ManagedServerError term so the failure is kind "endpoint": its base URL is marked dead for that walk only (profile-fallback.ts:205, a per-walk Set) and same-URL entries are skipped; other URLs continue. In-process, a supervisor failure is remembered per port for the rest of the command, so the other requests of a batch fail fast without new spawns; the next command tries again (auto-restart preserved).
- The 120 s stall rule applies to readiness only, never to an in-flight request.
- Platforms: darwin ps -ww -o command=; linux /proc/<pid>/cmdline split on NUL; win32 CIM CommandLine split by a double-quote-aware tokenizer; executable llama-server or llama-server.exe; spawn with windowsHide true; Windows stop ends the process at once and server-stop says so. Live: macOS here, Linux in CI; Windows parser tested only on recorded strings, stated unverified in the commit body until 2d.
- CI (own commit): ci.yml job build (ubuntu-latest) downloads llama-bNNNNN-bin-ubuntu-x64.tar.gz for one pinned tag (measured b11968, sha256 6f9e44cafe6d185e993741de35e2b24a2333132f980dadb378b09ded78a19f2f), checks the sha256, puts the extracted folder (binary plus its shared libraries) on PATH, and runs llama-server --version in the same step. The tag and update procedure are written in a workflow comment and on the 2d card.
- Tests added by this revision: (a) a managed model that reaches the spawn (-hf with a repo that does not exist) produces exactly one spawn, counted by the supervisor's per-spawn marker line in llama-server-<port>.log, and the final error contains ManagedServerError.message exactly once; (b) a failed run, then a fixed model, then the next run starts the server; (c) a profile with a managed primary and a fallback on a second URL reaches the fallback. The always-fail test ruling governs the suite when llama-server or the network is missing, not runtime fallback.
- Open measurement: llama-server -np defaults to -1 (auto); total_slots from GET /props is read in the 2a-core integration test and recorded.
