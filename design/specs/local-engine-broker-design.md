# Per-engine request broker, revision 2 (round-2 review done, its 3 blocking findings applied; decided under the /goal directive)

Cards: TRDD-1OOAH3LD, TRDD-ZGSGGHQG. Directives: 71ee3c3c (one model at a time, batching by model), e20f5690 (local only, calibrated rotation, no starvation timeouts), 8b492486 (main plus calibration server only).
Evidence: reports/llama-cpp-profile/20261028_203129+0100-scheduler-facts.md, round-1 review (4 blocking, all accepted).

Rationale: under the user's rules each local engine holds one model at a time; llm-ext groups queued requests from every running command by model, runs each model batch on one server, rotates the model after a calibrated batch, never starves a queue into timeouts, and never runs more than one main and one calibration server per engine. Remote profiles are unchanged.

1. Broker per engine (llama, locals): detached llm-ext child (spawnDetachedBench pattern, bench-spawn.ts:103), one per engine guaranteed by a broker pid file plus liveness check; state <config>/broker-<engine>.json (0600: pid, port, token, version, startedAt).
2. Loopback OpenAI-compatible proxy on 127.0.0.1 with a random token header; resolveConnection's hook (connection.ts:143) ensures the broker and returns its URL and token; request bodies unchanged except the broker sets the outgoing model field for the server it runs; no streaming on broker routes: the job result is returned whole when complete (a long prompt read sends no bytes, and undici's 300 s body timeout would cut a silent stream).
3. Batching works only if commands hand over batches: for broker routes the per-process one-at-a-time pool (index.ts:1117) is replaced by a per-command submission window W (provisional 2 x B), refilled as jobs complete, at every batch call site (index.ts:2581, 5186, 6108/6171, 6214/6322) and for ensemble members. Within a model's queue the broker takes jobs round-robin across commands, so one command's 1,000 files never block another command's single file. If the broker fails and the walk falls back to a remote model, the client re-applies that profile's normal pool.
4. Waiting is not a timeout, and no connection is held while queued: Node 26 global fetch (undici 8.12.2) has a 300 s default headers timeout and node:undici is not importable (measured), so llm-ext cannot set a per-request dispatcher without adding a dependency. The broker therefore uses submit and long-poll: POST /v1/jobs with the unchanged request body returns {job} at once; GET /v1/jobs/<job>?wait=60 returns the finished response (status and body, or a stream) or 204 after at most 60 s, so no HTTP exchange approaches the 300 s limit. A job not polled for 120 s is treated as abandoned and dropped before dispatch (this is how a cancelled command's requests leave the queue). The broker owns execution timeouts after dispatch (liveness rules) and reports a model-scoped failure as the job's result. The client side lives in chatCompletionSimple (completion.ts:511) for broker routes. Time queued in the broker is excluded from every client deadline (the retry clock, RetryDeadlineError, the soft timeout): deadlines count from the dispatch time the broker reports in each poll reply. Every client abort sends DELETE /v1/jobs/<job> (best effort; the 120 s rule is the backstop). A client retry reuses its job while it is pending; only a finished, failed job gets a new submission. The breaker, retries and fallback walk are otherwise unchanged.
5. Failure classification: a broker failure for model M marks (URL, M) dead for that walk, never the URL alone (rekey the per-walk Set in profile-fallback.ts ~205/242/254), so other models behind the same broker are still tried; a broker connection reset (broker dead) marks the whole URL dead.
6. Scheduling: one queue per model, one current model. Dispatch up to C for the current model (llama: server slots; Locals: max_parallel under the memory floor; low memory waits, never an error). Each job's deadline is its submit time plus its queue timeout: default T = 300 s (user ruling 2026-10-28), overridable per command with --queue_timeout=<seconds> (snake_case like every llm-ext flag), carried with each job; a long value (e.g. 99990 for a large job) means the job may wait. Rotation (coordinator decision 2026-10-28, binding): (1) with no current model, load the model whose oldest request waited longest; (2) when the current queue and in-flight are empty and nothing happened on the current model (submit, dispatch or reply) for a linger of 1 s (env-overridable; a sequential caller submits its next request first), rotate to the model whose oldest request waited longest; (3) any other rotation happens only when BOTH hold: (a) the current model has dispatched at least min(B, its queued count when it was loaded) requests, or has run at least D seconds (B and D are a MINIMUM slice, never a maximum, so after every swap the new model is served before the next swap), and (b) some other model's job has a deadline that has passed or falls within that model's last measured load time (60 s estimate before its first load; the broker records the load time per model); the rotation goes to the model holding the earliest such deadline. A job past its deadline never fails: waiting is never an error. B and D are calibrated per engine and model set to maximise throughput subject to every job's wait staying within its queue timeout; provisional B 32, D 180 s. Worst-case queue wait: about T + D (plus draining in-flight and one model load). Abandoned jobs (not polled for 120 s) are removed from the queue before dispatch.
7. Swap: stop the server (SIGTERM to its process group, SIGKILL after 10 s, process snapshot confirms the group is gone), start the next model at its calibrated context. Measured load: GGUF 4-60 s, Locals 4-8 s.
8. Server-count safeguard: a short-held registry lock guards a registry file of llm-ext servers per engine (role main or cal, pid, pgid, port, argv). At most one main (owned by the broker) and one cal (owned by calibration) per engine; any other spawn is refused with a clear error naming server-stop. Before every spawn: for each registry entry whose recorded pgid is alive and whose live argv still matches, it counts; entries with a dead pid are removed; an orphaned main (broker dead) is killed by its pgid before a new main starts. The registry entry is written right after spawn while the lock is held; a stable marker also finds an unrecorded llm-ext server (Locals cwd is the config dir; llama gets --log-file <config>/llama-server-main.log). Calibration and the broker may run at the same time; memory is the sum.
9. Locals start: <locals venv python> -I -m locals.server ..., cwd the config dir (hardened after the mlx.py shadowing incident). llama identity: argv (-hf / --hf-repo --hf-file / -m) compared to the target, not /v1/models.
10. Idle: llama-server keeps its built-in sleep (--sleep-idle-seconds 1800) inside the window; with no request for 2 hours the broker stops its server; a broker with no server and no request for 2 hours exits. A broker whose config dir no longer exists (coordinator decision 2026-10-29) stops its servers, fails its held jobs with the reason and exits on its next tick (1 s): a removed config or a deleted test dir never leaves a broker and its server holding RAM until the idle exit.
11. Version handover: the broker writes its llm-ext version; a client with a different version asks the old broker to stop accepting, drain and exit, then starts a new one.
12. Ensemble: members are separate requests grouped by model; a file merges after all members' batches; ensemble latency about three batches plus up to three swaps (told to the user).
13. Kept from the paused P1 tree: async lock, state files, argv identity, download-aware readiness, ManagedServerError final-stop, model-id parser, walker classification (changed to URL plus model). Dropped: per-route target, router mode.
14. Tests (real): two tiny GGUF models via one broker from two separate llm-ext processes: one load per model, A's requests before B's, never two main servers (process snapshots); rotation after B with T low; model A failing does not skip model B; an abandoned job (no poll for 120 s, test parameter) never executes; a wait longer than 300 s completes through repeated 60 s polls; a retry deadline shorter than the queue wait completes without error; an aborted request's job is cancelled and never runs; round-robin: a second command's single job is served before the first command's remaining batch ends; when the broker dies, in-flight jobs fail and the walker falls back; broker SIGKILL then the next start kills the orphaned main by pgid (snapshot); version handover; idle exit with a short window; Locals tests darwin only (disclosed); a job with a short --queue-timeout forces a rotation earlier than the default.
15. Command timeout (user ruling 2026-10-28): optional --command_timeout=<seconds> (also spelled --command-timeout or --timeout, with '=' or a space; a global flag every command accepts, user ruling 2026-10-28) limits the whole command (default no limit, local or remote). On expiry the command cancels (DELETE) every job it still has at the broker, stops submitting, writes the per-file results already complete, lists the unfinished files and exits non-zero. Test: a short --command_timeout exits non-zero and leaves no job queued at the broker.
