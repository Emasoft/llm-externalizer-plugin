## 2. What this is, in one paragraph

Add `mass-scouting` to llm-externalizer. The user supplies (a) a folder/glob of files and (b) a list of *fields* — each field is a `{name, type, description}` plus optional constraints (enum values, array item type, numeric range). The system **dynamically generates a strict JSON schema** matching that exact field set, **dynamically generates a prompt** that names each field and quotes each description, then fans the (file × schema) calls out to OpenRouter with `response_format: json_schema` and `qwen/qwen-2.5-7b-instruct`. Per-file results are written to a SQLite-backed registry that survives across runs, supports `--resume`, and is queryable with FTS5 + structured-column filters.

The existing `scan_folder` tool covers the "free-text per-file report" case. `mass-scouting` is the new "structured per-file extraction" case — same fan-out shape, different output contract, and persistent.

---

## 3. Why this is novel vs. the blueprint

The blueprint at `docs_dev/mass-scouting-blueprint.md` describes a fixed-schema pipeline (skill-manager). It scouts skills with a hard-coded schema (`summary, topics, language_iso, confidence`).

The user's twist is that **the schema must be different for every scout invocation**. Concrete examples we must support:

| Scenario | Field set the user defines |
|---|---|
| TS code audit | `{is_async:bool}`, `{frameworks:array_string}`, `{has_tests:bool}`, `{complexity_1_to_10:int}` |
| Markdown notes triage | `{topic:string}`, `{language_iso:string}`, `{actionable:bool}`, `{tags:array_string}` |
| Log severity classify | `{severity:enum(info,warn,error,security)}`, `{summary:string}` |
| Config audit | `{contains_secrets:bool}`, `{auth_method:enum(none,oauth,jwt,basic)}`, `{platforms:array_string}` |

Every one of those is a different schema. So the design centres on the **field-definition DSL → JSON schema → prompt** pipeline.

## 5. Field DSL — the core abstraction

### 5.1 Field type system

```
type FieldType =
  | { kind: "bool" }
  | { kind: "string"; max_length?: number }
  | { kind: "enum"; values: string[] }
  | { kind: "array_string"; max_items?: number }
  | { kind: "array_enum"; values: string[]; max_items?: number }
  | { kind: "int"; min?: number; max?: number }
  | { kind: "number"; min?: number; max?: number };

interface FieldDef {
  name: string;            // ^[a-z][a-z0-9_]{0,39}$  (snake_case, JSON-key-safe)
  description: string;     // 5-280 chars, used verbatim in prompt + schema description
  type: FieldType;
  required?: boolean;      // default true
  examples?: unknown[];    // optional, copied into the prompt as guidance
}

interface ScoutFieldset {
  version: 1;
  fieldset_name: string;    // human label, e.g. "ts-code-audit"
  fields: FieldDef[];
  notes?: string;           // freeform — placed before the schema in the prompt
}
```

### 5.2 TOML canonical form (example)

```toml
version = 1
fieldset_name = "ts-code-audit"
notes = "Audit TypeScript files for async/test/complexity signals."

[[field]]
name = "is_async"
type = "bool"
description = "True if the file declares or awaits any async/await construct (async fn, top-level await, .then chain on imported promise)."

[[field]]
name = "frameworks"
type = "array_string"
description = "Frameworks/libraries the file imports or extends (e.g. 'react', 'express', 'lodash'). Empty array if none."
max_items = 8

[[field]]
name = "test_kind"
type = "enum"
values = ["none", "unit", "integration", "e2e", "snapshot"]
description = "What kind of test (if any) this file is. 'none' if it is not a test."

[[field]]
name = "complexity_1_to_10"
type = "int"
min = 1
max = 10
description = "Subjective complexity score: 1 = trivial getter, 10 = nested concurrent logic."
```

### 5.3 CLI shorthand grammar

`--field 'NAME:TYPE=DESCRIPTION'` — type forms:

| Shorthand | Compiles to |
|---|---|
| `name:bool` | `{kind:"bool"}` |
| `name:string` | `{kind:"string"}` |
| `name:string(120)` | `{kind:"string", max_length:120}` |
| `name:enum(a,b,c)` | `{kind:"enum", values:["a","b","c"]}` |
| `name:array` | `{kind:"array_string"}` |
| `name:array(5)` | `{kind:"array_string", max_items:5}` |
| `name:int` | `{kind:"int"}` |
| `name:int(1-10)` | `{kind:"int", min:1, max:10}` |
| `name:number(0.0-1.0)` | `{kind:"number", min:0, max:1}` |

Description is everything after the first `=`. Quotes preserve spaces.

### 5.4 Schema generation (the deterministic compiler)

Pure function `compileFieldset(fs: ScoutFieldset) → { jsonSchema, prompt, validate }`:

```ts
function compileFieldset(fs: ScoutFieldset) {
  const properties: Record<string, JsonSchema> = {};
  const required: string[] = [];
  for (const f of fs.fields) {
    properties[f.name] = fieldTypeToJsonSchema(f.type, f.description);
    if (f.required !== false) required.push(f.name);
  }
  const jsonSchema = {
    name: `mass_scout_${fs.fieldset_name.replace(/[^a-z0-9_]/gi, "_")}`,
    strict: true,
    schema: {
      type: "object",
      additionalProperties: false,
      required,
      properties,
    },
  };
  const prompt = renderSystemPrompt(fs); // §5.5
  const validate = makeRequiredKeysValidator(required); // §5.6
  return { jsonSchema, prompt, validate };
}
```

`fieldTypeToJsonSchema` maps each `FieldType` to its JSON Schema fragment, copying `description` verbatim so the model sees it both in the prompt AND inside the schema (some providers honour schema descriptions when constraining).

### 5.5 Prompt template (rendered, system role)

```
You inspect a single file and extract structured information.

For the file body provided after FILE:, return a JSON object that EXACTLY
matches the schema below. Do not include any other keys. Do not omit
required keys. Output JSON only, no prose, no fences.

NOTES (from the user):
{{fs.notes ?? "(none)"}}

FIELDS TO EXTRACT:
{{ for each f in fs.fields }}
- "{{f.name}}" ({{renderType(f.type)}}): {{f.description}}
{{ end }}

If a field describes a property the file does not exhibit:
- bool fields: emit `false` (NOT null, NOT missing).
- string fields: emit "" (empty string).
- array fields: emit [].
- enum fields: pick the value the user listed for "absent/none" if it
  exists; otherwise pick the most defensible value and lean conservative.
- int/number fields: emit the lowest legal value in range.

Never invent facts. Read only the provided FILE body.
```

The user-role message is `FILE: <basename>\n\nCONTENT:\n<body[:max_excerpt_kb]>`.

### 5.6 Required-keys validator

Identical to blueprint §3.6 — built from `required` once at compile time. Catches the rare provider that returns `{}` after honouring `strict: true`.

### 6.2 SQLite schema (final, `registry.ts`)

```sql
CREATE TABLE IF NOT EXISTS file_short_id (
  short_id      INTEGER PRIMARY KEY AUTOINCREMENT,
  fingerprint   TEXT NOT NULL UNIQUE,           -- sha1(normalised content)
  file_path     TEXT NOT NULL,
  source_root   TEXT NOT NULL,
  basename      TEXT NOT NULL,
  classifier_bucket TEXT NOT NULL DEFAULT 'unknown',
  has_yaml_frontmatter INTEGER,
  detected_language    TEXT,
  detected_format      TEXT,
  file_size_bytes      INTEGER,
  created_at    TEXT NOT NULL
);
CREATE INDEX idx_fsi_path ON file_short_id(file_path);

CREATE TABLE IF NOT EXISTS mass_scout_jobs (
  job_id            TEXT PRIMARY KEY,           -- "scout-<ts>-<slug>"
  fieldset_name     TEXT NOT NULL,
  fieldset_json     TEXT NOT NULL,              -- the validated ScoutFieldset
  json_schema       TEXT NOT NULL,              -- the compiled JSON Schema
  model             TEXT NOT NULL,
  workers           INTEGER NOT NULL,
  source_root       TEXT NOT NULL,
  bucket_filter     TEXT,                        -- 'has_frontmatter' or NULL
  started_at        TEXT NOT NULL,
  ended_at          TEXT,
  files_total       INTEGER,
  files_ok          INTEGER,
  files_failed      INTEGER,
  retries           INTEGER,
  cost_usd          REAL,
  notes             TEXT
);
CREATE INDEX idx_jobs_started ON mass_scout_jobs(started_at);

CREATE TABLE IF NOT EXISTS mass_scout_results (
  job_id            TEXT NOT NULL,
  file_fingerprint  TEXT NOT NULL,
  short_id          INTEGER NOT NULL,
  result_json       TEXT NOT NULL,              -- the validated extraction
  raw_response      TEXT,                        -- pre-repair, for audit
  repaired          INTEGER NOT NULL DEFAULT 0,
  attempts          INTEGER NOT NULL DEFAULT 1,
  cost_usd          REAL,
  enriched_at       TEXT NOT NULL,
  PRIMARY KEY (job_id, file_fingerprint),
  FOREIGN KEY (short_id) REFERENCES file_short_id(short_id)
);
CREATE INDEX idx_results_short ON mass_scout_results(short_id);

-- Standalone FTS5 (per blueprint pitfall #2 — never use content= link).
CREATE VIRTUAL TABLE IF NOT EXISTS mass_scout_results_fts USING fts5(
  job_id UNINDEXED,
  file_fingerprint UNINDEXED,
  searchable_text,                              -- concatenated string fields
  tokenize='porter unicode61'
);
```

`searchable_text` is built at insert time by concatenating every field of type `string`, `array_string`, `enum` from the result. Boolean and numeric fields are queryable via JSON1 functions on `result_json` (or via materialised columns — see §11 follow-ups).

### 6.3 Concurrency + threading model in TS

Node doesn't share `better-sqlite3` connections across threads, but the simpler shape is **single-thread async I/O**: all OpenRouter calls are async fetch (event-loop-friendly), and SQLite writes happen on the main thread between awaits. `p-limit(256)` gates concurrent fetches. The Python "thread-local SQLite" pattern from blueprint §3.8 is not needed — we have one main-thread connection in WAL mode.

If contention shows up at >300 RPS we can switch to `worker_threads` later, but the empirical bottleneck in the blueprint was OpenRouter-side, not SQLite-side.

## 7. Compilation example end-to-end

User invokes:

```bash
llm-ext mass-scout scout --db /tmp/audit.db --fields-file ./fields.toml \
                          --workers 256 --i-confirm-cost
```

With `fields.toml` from §5.2 above.

1. **Load + validate fieldset** → `ScoutFieldset` object.
2. **Compile** to:
   - `jsonSchema`:
     ```json
     {
       "name": "mass_scout_ts_code_audit",
       "strict": true,
       "schema": {
         "type": "object",
         "additionalProperties": false,
         "required": ["is_async", "frameworks", "test_kind", "complexity_1_to_10"],
         "properties": {
           "is_async": {"type": "boolean", "description": "True if the file declares..."},
           "frameworks": {"type": "array", "items": {"type": "string"}, "maxItems": 8, "description": "Frameworks/libraries..."},
           "test_kind": {"type": "string", "enum": ["none","unit","integration","e2e","snapshot"], "description": "What kind of test..."},
           "complexity_1_to_10": {"type": "integer", "minimum": 1, "maximum": 10, "description": "Subjective complexity..."}
         }
       }
     }
     ```
   - `prompt`: rendered §5.5 with the four fields enumerated.
   - `validate`: required-keys validator on `["is_async", "frameworks", "test_kind", "complexity_1_to_10"]`.
3. **Smoke-test** 5 random files against the compiled schema. Abort if any fail.
4. **Cost estimate** vs. eligible file count. Print to stdout; require `--i-confirm-cost` if >10K.
5. **Fan out** at 256 workers via `p-limit`. Each call:
   - reads file body (capped at 4 KB by default, configurable),
   - calls OpenRouter `/chat/completions` with `response_format: {type: "json_schema", json_schema: <compiled>}`,
   - JSON-parses, runs validator, runs `fix_envelope` repairs (truncate over-cap strings, drop excess array items, coerce numbers into range — all logged),
   - on validator failure: re-prompts with the failure reason inlined, up to `--max-retries`,
   - inserts `mass_scout_results` row + writes JSONL telemetry line.
6. **Final report** at `<repo-root>/reports/mass_scouting/<TS±TZ>-scout-<job_id>.md` summarising files_ok/failed, total cost, top-N most-frequent values per field, and a histogram for numeric fields.

## 8. Failure-mode handling (lifted from blueprint §6, applied to dynamic schemas)

| Pitfall | Mitigation in v1 |
|---|---|
| Model returns valid JSON but missing keys | Required-keys validator + retry-with-feedback (blueprint §3.6/§3.7). |
| Schema describes `enum` but model emits unlisted value | `fix_envelope` snaps to nearest listed value if Levenshtein ≤ 2; otherwise retry. |
| String fields exceed `max_length` | Truncate at last word boundary; log repair. |
| Array exceeds `max_items` | Trim to limit; log repair. |
| Number out of range | Clamp; log repair. |
| OpenRouter says model supports json_schema but returns null | 5-call smoke test in step 3 above; abort with clear error. |
| Field name collides with SQLite reserved word | Field names are stored *inside* `result_json`, never as columns, so collisions are impossible at the DB layer. |
| Rate-limit window | Reuse the existing `mcp-server/src/index.ts` rate-limit + AIMD logic (already battle-tested at line ~1567+). |
| Buffered stdout in long runs | Pass `process.stdout.write` + flush; one progress line per 200 files (matches blueprint §6 row 1). |
| Mid-run abort / kill | Job is `--resume`-able: `mass_scout_results` PK on `(job_id, file_fingerprint)` makes resumption an `INSERT OR IGNORE`. |

## 9. Security / compliance items

- OpenRouter API key resolution stays as the existing `$OPENROUTER_API_KEY` / `CLAUDE_PLUGIN_OPTION_OPENROUTER_API_KEY` pipeline. No new secrets handling.
- `mass_scout_register` MUST honour the existing `scan_secrets` mechanism: pre-scan the body before sending. Default ON.
- Reports + JSONL telemetry are written under `reports/mass_scouting/`, which is already in the plugin `.gitignore` (verified line 21 of plugin `.gitignore`: `reports/`).
- File-path strings are stored as absolute paths in the registry — caller-controlled, but the registry is local-only by design. Document that the DB file should NOT be committed.

## 11. Out of scope for v1 (potential follow-ups)

- **Canonicalisation phase** — only valuable when fields produce taxonomy paths; defer until a user asks.
- **Promote phase** — confidence-threshold filtering; defer for the same reason (no `confidence` field is required by mass-scouting unless the user defines one).
- **Materialised columns** for boolean/enum/int fields so `--filter NAME=VALUE` runs index-fast without JSON1 scans. v1 uses `json_extract(result_json, '$.<name>')`. Optimise when corpus size warrants.
- **TUI / interactive fieldset builder** — nice-to-have; the TOML + shorthand cover the use case for now.
- **Multi-job join** — searching across two job_ids with different schemas. v1 search is per-job.

### File-size caps (final)

| Cap | Applies to |
|---|---|
| **40% of model context** | (a) any individual file fed whole-content to scout, (b) any sample-bytes value. Skip / refuse if exceeded. |

Both caps are a function of the active model's reported context window (resolved through the existing OpenRouter model-info infra). They are configurable via `--max-context-pct-scout` (default 0.40) and `--max-context-pct-register` (default 0.50) for callers who want to tighten further but not loosen.

### Regex-bypass heuristic for `mass_scout_search` / `mass_scout_search_xjob`

Detection order — first match wins:

1. **Explicit `--regex 'PATTERN'`** → run regex over the raw file bodies, return matches with line numbers and a 80-char surrounding snippet. Skip LLM entirely.
2. **Built-in named patterns** — query exactly equals or contains one of these phrases (case-insensitive, normalised whitespace):
   - "all emails" / "find emails" → `[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}`
   - "all urls" / "find urls" / "all links" → `https?://[^\s'"<>]+`
   - "urls of domain X" / "links to X" → `https?://[^\s'"<>]*<X-escaped>[^\s'"<>]*`
   - "all ipv4" / "all ip addresses" → `\b(?:\d{1,3}\.){3}\d{1,3}\b`
   - "all phone numbers" → `\+?\d[\d\s().-]{6,}\d`
   - "all hex colors" / "all hex colours" → `#[0-9A-Fa-f]{3,8}\b`
   - "all semver" → `\bv?\d+\.\d+\.\d+(?:-[\w.]+)?\b`
   - "all github repos" → `\bgithub\.com/[\w.-]+/[\w.-]+\b`
   - "all aws keys" → `\bAKIA[0-9A-Z]{16}\b` (read-only — flagged as security smell)
3. **No match** → fall through to LLM-backed FTS5 + structured-filter search (the per-job DB already has the answer if scout ran).

The regex bypass is implemented in TS using Node's native RegExp (file content already lives in the registry's `body_cache` table — no re-read). Each match path is tagged `mode: regex|llm` in the search report. Caller can override with `--force-llm` or `--force-regex`. (Implementation language note: user wrote "python regex" — I'm reading that as "programmatic regex" and implementing in TS to keep the stack single-language. Flag if you wanted a Python sidecar instead.)

### Token-frugality directives (Q2 elaboration)

User: *"do not waste tokens: avoid having to repeat or read things twice."*

Concrete code rules:
- File bodies are read **once** at register time, hashed, and the body is cached in `file_body_cache` (a separate table referenced by `file_short_id.fingerprint`). Scout, sample, and regex search read from the cache, never the disk.
- The TRDD itself is tracked; future sessions land on §15 first via the explicit "supersedes" note in the Status line and §15 header.
- The `--resume` path reads only the registry, never re-opens already-processed files.
- Reports are append-only (existing rule from `agent-reports-location.md`).
