# TRDD-f1510055-e5f8-4d20-8527-a238a90d0968 — Free-pool auto-benchmark on free_only switch with `--bench-free-pool` surface

**Filename:** `design/tasks/TRDD-20260527_194441+0200-f1510055-free-pool-auto-bench.md`
**Tracked in:** `Emasoft/llm-externalizer-plugin` (this repo)

## Context

`free_only` (TRDD-8b6b3646 / TRDD-97ef8b63) gives a user a one-flip
cost-safety mode: flip `free_only: true` in `~/.llm-externalizer/settings.yaml`
and the plugin refuses to send any non-`:free` model to OpenRouter.
The free pool is `free_models: […]` — N OpenRouter `:free` ids the
plugin will rotate through on rate-limit error.

The gap left after those TRDDs landed:

- **Nothing automatically scored the free pool.** The benchmark cache
  (`~/.llm-externalizer/benchmark-results.json`) was populated only
  when the user manually ran `/llm-externalizer:llm-externalizer-benchmark
  --include …` once per model. After flipping `free_only` ON, the
  cache typically held zero `:free` entries, so the user had no
  empirical basis to pick top-N free models or to know which seed
  ids actually returned valid output on their account.
- **The setup-time UX was wrong.** The plugin shipped a 15-model
  `FREE_POOL_SEED` constant (Phase 1 of this TRDD bumped the
  `remote-free-ensemble` template from 6 → 15 entries) but never
  *exercised* those ids end-to-end. A user switching to
  `remote-free-ensemble` had to trust a list they hadn't validated.
- **The benchmark CLI required N invocations to score a pool.** No
  single-flag entry to "score every model in the active profile's
  free pool" — the user had to manually type 15 `--include` flags.

The user (verbatim): "now add a switch in the ~/.llm-externalizer/settings.yaml
to only use free models on openrouter. benchmark all free models
automatically when the user switch, starting by the following models:
[15 free models listed]"

## Decision

Ship two coupled deliverables that close the gap end-to-end:

**Surface delivery — `--bench-free-pool`** (TRDD's user-visible half):
single CLI flag on `llm-ext-benchmark` that resolves the candidate
set from the active profile's `free_models` (or `FREE_POOL_SEED` if
the profile pins no list), refuses any non-`:free` id, and feeds the
result into `--include` (keyword mode) or `--model` (security-triage
mode). Three surfaces:

  - **CLI:** `node dist/benchmark.js --bench-free-pool`
  - **Slash command:** `/llm-externalizer:llm-externalizer-bench-free-pool`
  - **No MCP tool** (by design — the MCP server is *read-only*; running
    a 10-30 min benchmark from a tool call would violate that. See
    "Why no MCP tool" below.)

**Auto-trigger** (the TRDD's "automatic" half): on MCP server boot
AND on every live `settings.yaml` reload, if `free_only` is now ON
and the benchmark cache holds no `:free`-suffixed entries, the
server spawns a **detached** process running `node dist/benchmark.js
--bench-free-pool --min-f1 0.5` in the background. The bench writes
to `~/.llm-externalizer/free-pool-bench.log` and records its PID in
`~/.llm-externalizer/free-pool-bench.lock`. The MCP server returns
to its event loop immediately.

## Why no MCP tool

The other tools the plugin exposes (`chat`, `scan_folder`, etc.) all
have these properties:

- They complete in seconds to a few minutes per call.
- They are *the agent's* operation — the orchestrator decides when
  to call them; the user pays per call in their own context.
- They are read-only or write-to-disk-and-return-a-path.

A benchmark sweep has the opposite shape:

- 10-30 minutes per run (15 models × ~60s each for the keyword task,
  more for security-triage).
- The user wants it to fire on a settings change, not on an agent's
  whim — the orchestrator should not be deciding to burn 30 minutes.
- It writes a cache the WHOLE plugin reads, not just the calling
  agent.

Exposing it as an MCP tool would be a footgun: any agent could
trigger a half-hour blocking operation. The slash command + CLI +
auto-trigger triad covers every actual user workflow without that
hazard. (See user-global rule: "every capability ships as MCP tool +
CLI command + slash command, same core logic" — auto-trigger acts as
the MCP-equivalent fourth surface here.)

## Implementation

### A. `--bench-free-pool` CLI flag

File: `mcp-server/src/benchmark/index.ts`

- Import `FREE_POOL_SEED` from `config.js`.
- Add `benchFreePool: boolean` to `CliOptions`.
- Parser branch: `--bench-free-pool` → `opts.benchFreePool = true`.
- In `main()`, after `setActiveFreeOnly(resolved.freeOnly)`, capture
  `activeFreeModels = resolved.freeModels`. If `opts.benchFreePool`:
    1. Pick pool from `activeFreeModels` if non-empty, else `FREE_POOL_SEED`.
    2. Validate every entry ends with `:free`. Throw if not.
    3. Append each pool id to `opts.triageModels` (security-triage
       mode) or `opts.includeIds` (keyword mode). De-dup against any
       explicit `--include`/`--model` the user passed alongside.
    4. Log pool source to stderr.

### B. `/llm-externalizer-bench-free-pool` slash command

File: `commands/llm-externalizer-bench-free-pool.md`

Thin wrapper around the CLI, identical pattern to
`commands/llm-externalizer-benchmark.md`. Documents that `--dry-run`
skips auth and that composing with `--security-triage` runs the
triage benchmark on the same pool.

### C. Auto-trigger module

File: `mcp-server/src/free-pool-auto-bench.ts` (new)

Exports `maybeTriggerFreePoolBench(opts)`. Pure function (modulo
the spawn() side effect at the end). Skip conditions evaluated in
order:

1. `freeOnlyActive === false` → no auto-bench needed.
2. `env[LLM_EXT_DISABLE_FREE_POOL_AUTO_BENCH] === "1"` → opt-out.
3. Benchmark cache has any `:free`-suffixed entry → already scored.
4. Lock file exists AND holds a live PID → another bench is running.
5. `freeOnlyWasOn === true` (settings reload) → not a transition;
   only fire on OFF→ON (or startup, when prior state is unknown).

Otherwise: spawn `node <benchmark.js> --bench-free-pool --min-f1 0.5`
detached, stdio piped to `~/.llm-externalizer/free-pool-bench.log`,
PID recorded in `~/.llm-externalizer/free-pool-bench.lock`.

### D. Wire into MCP server lifecycle

File: `mcp-server/src/index.ts`

Two call sites:

1. **Startup IIFE** (line ~1357): after `setActiveFreeOnly(resolved.freeOnly)`,
   call `maybeTriggerFreePoolBench({ activeProfile, freeOnlyActive,
   freeOnlyWasOn: null, log: process.stderr.write })`. `freeOnlyWasOn: null`
   tells the helper this is startup, not a transition.
2. **Settings-reload path** (`reloadSettingsFromDisk`, line ~1849):
   capture `priorFreeOnly = activeResolved?.freeOnly ?? false` BEFORE
   the atomic swap, then after `setActiveFreeOnly(nextResolved?.freeOnly
   ?? false)` call `maybeTriggerFreePoolBench({ …, freeOnlyWasOn:
   priorFreeOnly })`.

### E. 429 retry in benchmark runner

File: `mcp-server/src/benchmark/runner.ts`

Without retry, every free-tier 429 (rate-limit) records as a hard
ERR on first attempt. Free-pool benchmarks then look mostly broken
even when the issue is just transient throttling. Added a 3-retry
loop with exponential backoff (5s → 10s → 20s, capped at 60s, honoring
`Retry-After` header when present). Non-429 HTTP errors skip retry.
Cost-safety: the existing `getActiveFreeOnly()` chokepoint guard
runs BEFORE the fetch, so retries cannot bill in any scenario.

### F. Test coverage

File: `mcp-server/src/free-pool-auto-bench.test.ts` (new — 13 tests)

Pure offline tests with injected paths and a no-op script stub:

- Skip on `freeOnlyActive = false`
- Skip on `LLM_EXT_DISABLE_FREE_POOL_AUTO_BENCH=1`
- Skip when cache already has `:free` entries
- Skip when cache has only non-`:free` entries (should NOT skip)
- Skip when `freeOnlyWasOn = true` (not a transition)
- Skip when lock holds current process's PID (live-pid case)
- Ignore stale lock (PID 99999999, doesn't exist) → spawn anyway
- Spawn on real OFF→ON transition with no cache
- Spawn on startup (`freeOnlyWasOn = null`) when free_only is on
- Return shape on every path
- Tolerate non-JSON cache as empty
- Tolerate cache with non-array `results` field as empty
- Tolerate garbage lock file as stale

## Empirical findings (in-progress run)

The first real `--bench-free-pool` sweep (background task
`b6ob8svgr`, log `/tmp/free-bench-keyword-v2.log`) confirms:

- **Most free-tier models are daily-rate-limited.** The retry loop's
  60s cap helps with transient bursts but cannot recover from a
  full-day quota exhaustion (which is what most free models hit).
  Recommendation: re-run the sweep next day, or split it across
  multiple accounts.
- **`poolside/laguna-m.1:free` returns valid output** (88.5% F1 in
  v2, 89.6% F1 in the prior v1 run — variance is the model's, not
  the bench's, since temperature=0).
- **`nvidia/nemotron-3-super-120b-a12b:free` returns empty content**
  (no `choices[0].message.content`) — the bench correctly records
  this as ERR rather than a fake-pass.
- **Two paid candidates the discovery filter surfaced (`deepseek/
  deepseek-v4-pro`, `xiaomi/mimo-v2.5-pro`) 403 with "Budget limit
  exceeded".** That's the user's OpenRouter account state (paid
  monthly cap), not a project bug — and exactly why `free_only`
  exists.

## Cost-safety chain

The auto-bench cannot bill any paid model. Three independent guards
must all fail simultaneously for a paid HTTP call to leak through:

1. **`--bench-free-pool` argument validator** rejects any non-`:free`
   pool entry at CLI parse time (before any fetch).
2. **Runner's `getActiveFreeOnly()` guard** (TRDD-97ef8b63) rejects
   any non-`:free` model at request build time — even if the CLI
   somehow accepted one.
3. **OpenRouter's own per-model billing classification** — `:free`-
   suffixed models are billed at $0/M regardless of count or
   reasoning effort.

Belt + suspenders + belt. Plus the `LLM_EXT_DISABLE_FREE_POOL_AUTO_BENCH=1`
env-var escape hatch lets the user disable auto-spawn entirely.
