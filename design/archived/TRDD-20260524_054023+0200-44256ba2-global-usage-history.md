# TRDD-44256ba2 — Global usage history log

**Filename:** `design/tasks/TRDD-20260524_054023+0200-44256ba2-global-usage-history.md`
**Tracked in:** this repo.

## 0. User's request (verbatim, after two clarifications)

> make the llm-externalizer save a global history of every request done … save
> it in the home folder (~/.llm-externalizer/) … in the form:
> `TIMESTAMP - PROJECT-DIR - TOOL/COMMAND NAME (with params) - SUCCESS/FAIL - DURATION - COST`

Explicit scope correction from the user: this is a **flat, append-only,
human-readable history** — **ONE line per individual LLM WEB REQUEST**. **NOT**
cost accumulation, NOT per-project/model totals, NOT a query/analytics surface,
NOT JSON. The `COST`/`DURATION`/`SUCCESS|FAIL` columns are for THAT single web
request, not a per-invocation sum. (The user: *"if it is a problem aggregating
the requests, just record each request"* — so per-request is the chosen,
simpler design; no accumulator.) See [[no-overengineering-simple-requests]] — an
earlier over-engineered per-invocation-summing proposal was simplified away.

## 1. Exact line format

```
<TIMESTAMP> - <PROJECT-DIR> - <TOOL/COMMAND (params)> - <SUCCESS|FAIL> - <DURATION> - <COST> - <OP-ID>
```

- `OP-ID` — per-INVOCATION correlation id (`op-<8 hex>`, generated once in
  dispatchCallTool / CLI dispatch). EVERY web-request line emitted during one
  tool/command invocation shares the same OP-ID, so all requests of one call can
  be grouped later (`grep <op-id> history.log`). A request with no active
  invocation context gets a fresh standalone OP-ID. The aggregation **command**
  is explicitly DEFERRED (the user: "we can always aggregate them later") — only
  the id is added now; do NOT build a query/aggregation surface.

- `TIMESTAMP` — local time + GMT offset, ISO-ish `YYYY-MM-DDTHH:MM:SS±HHMM`
  (matches the repo timestamp convention; sortable).
- `PROJECT-DIR` — absolute path of the requesting project: `CLAUDE_PROJECT_DIR`
  if set, else the git top-level of cwd, else cwd.
- `TOOL/COMMAND (params)` — the MCP tool / CLI command name + a COMPACT param
  summary: scalar args inline, long strings truncated to ~80 chars, arrays
  shown as `name[N]`, secrets redacted (reuse the redaction patterns). Never
  dump a whole snippet/file body into the log line.
- `SUCCESS|FAIL` — `SUCCESS` if the handler returned, `FAIL` if it threw.
- `DURATION` — wall-clock of the invocation, `<N>ms` (or `<N.N>s` ≥ 1000ms).
- `COST` — USD cost of that invocation, `$0.000000` (6 dp). `$0.000000` when
  the invocation made no billed call (local model, cached, free, or a
  read-only utility).

File: `~/.llm-externalizer/history.log` (config dir via `getConfigDir()`;
honors `LLM_EXT_CONFIG_DIR`). Append-only, created on first write.

## 2. Design

### 2.1 Single chokepoint for line assembly
`dispatchCallTool(name, args, extra)` (index.ts:5601) is the ONE function every
MCP tool flows through (the mass_scout short-circuit at :5638 is INSIDE it).
Wrap its body:
```
start = Date.now(); project = resolveProject();
costStore.run({ usd: 0 }, async () => {
  try { result = await <existing dispatch>; ok = true; }
  catch (e) { ok = false; throw e; }
  finally {
    appendHistoryLine({ start, project, name, params: summarize(args),
                        ok, durationMs: Date.now()-start,
                        costUsd: costStore.getStore().usd });
  }
});
```
The CLI surfaces (`src/cli.ts`, `mass_scouting/cli.ts`, `cluster/cli.ts`,
`benchmark/index.ts`) get the SAME wrap at their top-level command dispatch so
direct-CLI invocations are logged too (the command name + argv → the
`TOOL/COMMAND (params)` field).

### 2.2 Per-request line (AsyncLocalStorage carries READ-ONLY context)
A new `usage-history.ts` module exports an
`AsyncLocalStorage<{tool, params, project}>` (`ctxStore`) +
`recordRequest({ok, durationMs, costUsd})` (reads `ctxStore`, appends ONE line)
+ `appendHistoryLine(...)` (atomic append) + `resolveProject()` +
`summarizeParams(args)`.

`dispatchCallTool` (and CLI dispatch) set the context ONCE per invocation via
`ctxStore.run({tool, params, project}, ...)` — they do NOT write a line
themselves. Each billed LLM call site calls `recordRequest(...)` when its single
HTTP call completes/fails, writing one line with THAT request's ok/duration/cost:
- main pipeline chat/code_task/scan_folder/compare/check_*/search_existing
  (the shared OpenRouter call path in index.ts).
- `mass_scouting/scout.ts` (per-file scout request).
- `security_scan/judge.ts` (per-batch judge request).
- `cluster/*` LLM phase requests.
- `benchmark/runner.ts` (per-model benchmark request).
No cost accumulation. AsyncLocalStorage only carries read-only context so each
request attributes to the right originating tool even under concurrency. A tool
that makes zero web requests writes zero lines (correct — the log is of WEB
REQUESTS). A `recordRequest` with no active context logs project + "(direct)".

### 2.3 Atomic, concurrency-safe append
`appendFileSync(path, line + "\n", { flag: "a" })` — POSIX `O_APPEND` makes a
single `write()` of one line atomic across processes. One line is well under
PIPE_BUF, so interleaving is not a concern. Failure to write history MUST NEVER
fail or slow the tool call — wrap in try/catch, swallow + (debug-log only).

### Surfaces (per [[three-surfaces-per-function]])
The logger is passive (writes on every call) — there is no "invoke" verb. The
user did NOT ask for a query tool, so DO NOT build one. The only optional
read-surface, if cheap: nothing. Keep it minimal.

## 4. Test scenarios
- Line shape exactly matches §1 for a SUCCESS call (all 6 fields, separators).
- A throwing handler → `FAIL`, duration present, line still written.
- Param summary: long string truncated; array → `name[N]`; an embedded secret
  redacted; nested object keys kept, values compacted.
- Cost: two `recordCost(0.001)` + `recordCost(0.0005)` in one invocation →
  `$0.001500`; zero billed calls → `$0.000000`.
- Concurrency: two overlapping invocations (AsyncLocalStorage) do not mix costs.
- Config dir created if missing; `LLM_EXT_CONFIG_DIR` honored.
- History write failure (e.g. unwritable dir) is swallowed — the tool result is
  unaffected.

## 5. Security / safety
- Redact secrets in the param summary before writing (the log lives in the
  user's home — still must not capture API keys passed as args).
- Never write the full snippet/file body (truncate) — avoids leaking source +
  keeps the log readable.
- History failure never propagates to the tool call (fail-open on LOGGING only,
  never on the actual work).
