# TRDD-V32LB992 — free-pool hygiene

Split out of [[TRDD-HKXRJT9X]], which was withdrawn when its own premise
(ox-alpha is fast) was refuted by measurement. The measurement's *incidental*
findings are the real defect and are recorded here instead of dying with that
card.

## 1. Verified facts (live probe, 2026-08-26)

Every `free_models` member was sent one real production-shaped chunk
(provider-reported `prompt_tokens` ≈ 24.7k — the true
`DEFAULT_MAX_CHUNK_TOKENS` payload). Raw rows:
`reports/model-matrix-bench/20260826_112129+0200-model-matrix.md`.

**10 of 17 members answered with usable content. 7 did not:**

| member | failure | robustness of the finding |
|---|---|---|
| `thinkingmachines/inkling:free` | HTTP **403** | **STRONG** — an account-access fact, not a transient. This account cannot use it at all. |
| `thinkingmachines/inkling-small:free` | HTTP **403** | **STRONG** — same. |
| `google/gemma-4-26b-a4b-it:free` | HTTP 429 | weak — may be transient or self-inflicted |
| `google/gemma-4-31b-it:free` | HTTP 429 | weak — same |
| `poolside/laguna-xs-2.1:free` | HTTP 429 | weak — same |
| `z-ai/glm-5.2:free` | HTTP 429 | weak — same |
| `nvidia/nemotron-3-nano-omni-30b-a3b-reasoning:free` | upstream `ResourceExhausted` | weak — provider-side |

Plus one member that answers but is **useless for summarization**:
`nvidia/nemotron-3.5-content-safety:free` returned **17 content chars** (with
1017 reasoning chars) on a 25k chunk. It is a content-safety classifier sitting
in a general summarization pool.

## 2. Scope — deliberately narrow

**IN:** evict the two 403 members and the content-safety member. Those three are
justified by evidence that does not depend on timing, load, or a single draw.

**OUT (explicitly):** evicting the 429 members. That evidence is weak — the same
sweep issued ~40 free-tier requests, so some 429s were plausibly self-inflicted,
and a daily quota resets. Evicting on one bad draw would shrink the pool for a
transient. Re-measure with replication on a quiet key before touching them.

**OUT:** any latency-based ranking or pruning. The probe is **n=1 per model**
and measured one model (`dots-3-note-preview`) at 66s and 297s on the same
payload — a 4.5x intra-model swing. No ordering claim survives that. Anyone
pruning on latency must replicate first.

## 3. The open question this card does NOT answer — ANSWERED 2026-08-27, see §3c

`free-cooldowns.json` held **0 active cooldowns** — every record expired —
while four members were live-429ing. It is tempting to conclude "the selector
therefore believes all 17 are healthy and burns an attempt per chunk
rediscovering otherwise", and that would make pool rot a direct cause of slow
compact. **That was never observed.** The probe used a bare `urllib` path with
no rotation, cooldown consult, hedging or retry — i.e. NOT the product's
selector. The selector may already skip these, or retry them successfully.

Establishing it requires instrumenting the real selection path and watching it
choose. Until then this is a hypothesis, and this card must not be cited as
having proved it.

**Superseded by §3c — the hypothesis is now confirmed by reading the selection
path. §3's caution stands as written and was correct to make.**

## 3c. §3 answered — the primary selector never consults cooldowns (2026-08-27)

Traced the real selection path. **The hypothesis in §3 holds.** Three
load-bearing facts, each read first-hand rather than taken from the trace
report that surfaced them (`reports/v32lb992-selector-trace/20260827_150255+0200-selector-trace.md`):

1. **`selectFreeEnsembleModels` (`free-rotation.ts`) cannot consult a
   cooldown.** It is a pure function of `(freeModels, catalogById,
   benchmarkFailed, benchEvidence)` — it takes no store, calls no cooldown
   lookup, and its whole body is
   `rankFreeModelsByBenchEvidence(filterFreeModels(...), ...).slice(0, 3)`.
   The three primary ensemble slots are chosen without any liveness input.
2. **A 403 can never enter the cooldown store.** The string `403` does not
   occur ANYWHERE in `free-rotation.ts` — so `classifyUnavailable`, whose
   verdicts are `daily-quota | gone | transient | null`, has no branch that
   could match one and returns `null`. `applyUnavailable` is therefore never
   reached for a 403. This confirms §3b.2's surviving reasons by a second,
   independent route (absence of the token, not inspection of the branches).
3. **Cooldowns REORDER, they never EXCLUDE.** `orderByAvailability` has
   exactly one call site, `orderedFreeAttempts`, which returns
   `[...fresh, ...deferred]` — a cooled member is pushed to the back and
   still attempted. This is `free-rotation.ts` invariant 2 ("a pool must
   degrade, not empty") behaving exactly as §3b.1 said it would, and it is
   why a denylist was the wrong shape.

**Consequence — CORRECTED the same day, see §3c.1 below. The original wording
("re-picked as a PRIMARY slot on every call/chunk, forever") overstated what
the three facts support and is retracted.** What they support: nothing can
ever EXCLUDE a 403 member, so it stays permanently ELIGIBLE and is picked
whenever the ranking puts it in the top 3. Whether it is in the top 3 is a
separate question about ledger state, which §3c did not measure before
asserting it. The one place the 403 IS durably recorded — the 24 h model-events
ledger — deliberately excludes 403 from `ROTATE_WORTHY_STATUSES`
(`model-events.ts:265`), for the stated and correct reason that a 403
normally means a bad API key, which rotating a model cannot fix. That
reasoning is sound for its intended case and simply does not fit a
MODEL-scoped 403, which is the mismatch §3b.3 already named.

**Still UNVERIFIED, and deliberately not inferred:** the cost. "Burns an
attempt per chunk" is the SHAPE of the defect; the actual wall-clock and
token cost of those wasted attempts has not been measured, so this card
still must not be cited as having proved that pool rot is why compact is
slow. That needs a timed run, not more reading.

**No fix shape is proposed here.** §3b.1–3b.3 killed three of them by
reading the mechanism; the remaining design call is genuinely open.

## 3c.1 — FIFTH retraction: the 403 members are not currently being picked

§3c asserted the 403 members are picked "on every call/chunk, forever". That
was a consequence INFERRED from three verified facts, not an observation —
the same substitution this card has now made five times, committed one hour
after I committed a lesson about it.

**Observed instead.** Ran the product (`llm-ext llm summarize <file>
--max_chars 100`, free profile, $0) and read which models it announced as its
ensemble slots:

```
Model poolside/laguna-xs-2.1:free supports: …
Model nvidia/nemotron-3-ultra-550b-a55b:free supports: …
Model cohere/north-mini-code:free supports: …
```

Three slots, and **neither `thinkingmachines/inkling:free` nor
`inkling-small:free` is among them** — though both are still in `free_models`
(indices 13 and 14 of 17, read from settings.yaml the same minute).

**What survives, precisely:** the MECHANISM is exactly as §3c describes —
nothing can exclude a 403 member, so it stays permanently eligible and
carries no memory of having failed. What does NOT survive is the claim that
this costs an attempt on every call. In the observed run it cost nothing,
because ranking placed both dead members outside the top 3. The waste is
CONTINGENT on ranking, not continuous.

**n=1**, and ranking depends on ledger state that changes — so this is not
proof they are never picked either. Both directions now rest on one
observation apiece, which is the honest state.

**Consequence for the fix decision:** the defect is real but LATENT — a
permanently uncallable model sits in the pool with no mechanism able to
remove it, and becomes live waste the moment ranking promotes it. That argues
for fixing it as rot-prevention, not as a present cost, and it removes
"compact is slow because of this" from the table entirely.

## 3c.2 — the ledger-write prerequisite: RESOLVED, it does happen

§3c.1 flagged an untraced link: does a free-pool 403 produce a
`non_retryable_failure` model-event at all? It matters because a proposed fix
(§3d) is built on that event existing. **Answer: yes, on all three free-pool
entry points.** Traced at source, not taken from the report that raised it:

- **The write itself** — `provider/completion.ts:476-478`:
  `if (res.status >= 400 && res.status < 500 && res.status !== 429) {`
  `appendModelEvent(conn.model || "unknown", "non_retryable_failure",`
  `` `HTTP ${res.status}`); }`` — then throws. A 403 satisfies the condition,
  and the write precedes the throw, so nothing in `free-rotation.ts`'s catch
  can suppress it. It is the ONLY `non_retryable_failure` write site outside
  `model-events.ts` itself.
- **`chatCompletionSimple`** (`completion.ts:350`) is the function containing
  it; **`chatCompletionJSON`** carries its own equivalent 4xx branch.
- **All three `callWithFreeRotation` sites reach one of them:** `index.ts:2366`
  and `:2854` (via `callOne`, defined `:2543`) both inject
  `chatCompletionWithRetry`, which calls `chatCompletionSimple`; `:2402`
  injects `chatCompletionJSON` directly.

**Correction to the trace report that raised this** (`reports/v32lb992-ledger-trace/`):
its conclusion is right, but it states the injected `callOne` *is*
`chatCompletionSimple`/`chatCompletionJSON`. For two of the three sites it is
`chatCompletionWithRetry`, one hop earlier. The hop happens to preserve the
answer; it was checked rather than assumed, because on this card a chain
that "obviously" reaches its destination is precisely what has gone wrong
five times.

**Consequence:** the fix in §3d has no missing first step — the event it
needs is already being written. What remains is what §3b.3 already
established: `ROTATE_WORTHY_STATUSES` deliberately ignores it.

## 3b. Mechanism finding — a settings edit alone is NOT durable (2026-08-26)

Deleting the three members from `free_models` in `settings.yaml` does **not**
evict them. The pre-scan reconcile re-adopts them on its next fire.

Verified in source, `model-reconcile.ts:147-162` — the adoption filter is:

```ts
const newFreeModels = catalogFreeQualified.filter(
  (id) => isFreeSuffixModelId(id) && !pooled.has(id) && !benchmarkFailed.has(id),
);
```

Removing an id from the pool flips `!pooled.has(id)` to **true**, so a live,
context-qualifying `:free` id comes straight back.

**The qualification gate was read, not inferred.** `catalogFreeQualified` comes
from `filterFreeModels()` (`free-rotation.ts:90-102`), whose only requirement
is `ctx >= FREE_FLOOR_MIN_CONTEXT_TOKENS`, and that floor is **32,000** —
deliberately lenient, documented as "NOT the 128K premium bar … a 128K floor
would empty most pools". All three targets clear it (`inkling` /
`inkling-small` 1,048,576; `content-safety` 128,000), so nothing in the
predicate stops re-adoption. The filter is lenient in the other direction too:
an id absent from the catalog, or carrying no context info, is **kept**.
(Logic verified in source; a live re-adoption was not observed.)

**The one existing exclusion hook is `benchmarkFailed`** — "never adopted,
dropped if present" (`model-reconcile.ts:65-66`), which is structurally exactly
what this card needs. **It must NOT be reused.** It is
`benchmarkFailedModels()` from `benchmark/security-triage/index.ts:206`, backed
by the **security-triage** verdict cache: entries are keyed `model::case` and a
model counts as failed only via `!inconclusive && !pass` on a real triage run.
Writing a synthetic failing verdict to evict a model that returned HTTP 403
would corrupt a genuine security dataset with a fact it never measured, and
would misreport that model's security posture forever after.

**Consequence:** acceptance item 2 ("a real test asserts a 403 member is not
re-admitted by pool auto-population") cannot be satisfied without a new,
honestly-named exclusion surface. There is none today — `config.ts`,
`model-reconcile.ts` and `free-rotation.ts` contain no denylist/exclude field
(grepped 2026-08-26). So this card's IN scope is **not** a 3-line settings
delete; it is a config-schema addition plus a reconcile filter change.

### 3b.1 A denylist is the WRONG shape — the codebase already forbids it

An earlier draft of this section proposed a `free_pool_denylist:` config field.
**That contradicts a documented design invariant and must not be built.**

The load-bearing citation is the task-#189 comment block, which states the rule
for this exact situation outright. (`free-rotation.ts` invariant 2 — *"NEVER
WORSE THAN NO REGISTRY … when every candidate is cooling we still PROBE
instead of hard-failing"* — points the same way, but its literal scope is
**cooldown probing**, not config; on its own it would not settle the question.
Weigh the #189 line, not the invariant, when revisiting this.)

> The cure is RANKING, never hard exclusion — invariant 2 above: **a pool must
> degrade, not empty.**

That comment also **already names this card's third target**. On 2026-08-05 the
auto-selected free trio (`laguna-xs`, `north-mini-code`,
`nemotron-3.5-content-safety` — "a SAFETY CLASSIFIER") was found producing
length+empty on nearly every code-review call, while per-tool ledgers carried
`qualified: false` rows for all three the whole time. The diagnosis this card
re-derived independently at §1 is four weeks old, and the prescribed cure was
built: a **bench-evidence ranking** tier (`BenchVerdict`, `qualityPass` on the
per-tool ledger rows) where a passing bench outranks never-benchmarked, which
outranks a real failing verdict, preserving operator order within a tier.

**Corrected direction — two distinct problems, not one:**

1. **`content-safety`** (answers, but uselessly) is a RANKING problem and the
   ranking machinery exists. The open question is why the existing tier did not
   already demote it — a per-tool ledger row that never got a `qualityPass`
   verdict, or a fold that is not consulted on this path. Investigate before
   writing anything new.
2. **The two 403 members** (`inkling`, `inkling-small`) are a different class:
   not low-quality output but **no access at all** on this account. Ranking
   cannot help — every draw costs a wasted request. **This class has NO
   existing home.** (An earlier draft of this item proposed a "persistent,
   long-lived cooldown" in `free-cooldowns.json`. That was inferred from the
   module's stated purpose, not from its code, and reading the code refutes it —
   see 3b.2.)

Item 1 has a home and needs investigation. Item 2 needs a mechanism that does
not exist yet. Neither is decided here. Both must satisfy the named constraint:
**the pool degrades, it never empties.**

### 3b.2 `free-cooldowns.json` cannot hold a 403 — for two independent reasons

Read in `free-rotation.ts`, not inferred:

**(a) No cooldown is permanent.** Every entry is
`{until: <epoch ms>, kind, strikes, detail}` (`:436-443`) and
`computeCooldownUntil` (`:558-566`) bounds all three kinds:

| kind | ceiling |
|---|---|
| `daily-quota` | next 00:00 UTC (≤ 24 h) |
| `gone` | `GONE_MS` = **1 hour** |
| `transient` | `TRANSIENT_CAP_MS` = **5 minutes** |

`pruneExpired` (`:610-616`) drops every row with `until <= now` and runs on each
load (`:705`). A non-expiring entry is not expressible without changing that
store's contract.

**(b) A 403 never reaches the store at all.** `classifyUnavailable` (`:500-540`)
has branches for daily-quota, `gone` (404 / no endpoints), and transient
(429 / 5xx / overload) — and **no 403 branch**. It returns `null`, and
`applyUnavailable` (`:571-575`) returns the store **unchanged** on `null`, by
design: *"a real bug must never silently cool a healthy model."*

Both reasons are confirmed against the **whole** function: `classifyUnavailable`
runs `:471-540`, and its head (`:471-502`) holds only the circuit-breaker guard
and the daily-quota branch. There is no 403 branch anywhere in it.

**Scope of that conclusion: the COOLDOWN REGISTRY only.** An earlier draft of
this paragraph said a 403 was "invisible to the whole availability system" and
"retried forever". **Both were false** — see 3b.3.

Note this refines, but does not replace, §3's open question: §3 observed *429*
members with no cooldown rows, and 429 **is** classifiable, so expiry remains
the likely explanation there. The 403 members would show no row under any
circumstances.

### 3b.3 403 IS handled — elsewhere, and as an ACCOUNT-wide fact

The opposite of the retracted headline is closer to true. Two other layers
handle 403 deliberately:

| site | behavior |
|---|---|
| `index.ts:1612` | `/API error 403\b/` → `{unrecoverable: true, serviceLevel: true, reason: "Access forbidden"}` |
| `index.ts:1743` (a `serviceLevel` consumer) | sets `aborted = true`, `abortReason = "Unrecoverable service error on <file>: Access forbidden"` |
| `model-events.ts:265` | `ROTATE_WORTHY_STATUSES = [400, 404, 410, 422]` — 403 **deliberately excluded** (see below) |

So a 403 does not vanish and is not retried forever. On the `classifyError`
path it **aborts the batch**.

**Two different rotations — do not conflate them** (an earlier draft did):
`free-rotation.ts` does per-call free-pool rotation; `model-events.ts` decides
whether a model is *persistently broken* from `non_retryable_failure` events
over a 24 h window. `ROTATE_WORTHY_STATUSES` gates only the latter.

**The real defect this card should carry.** Those layers model 403 as an
**account-wide** fact. The `model-events.ts:244` comment says so in full — quoted
verbatim, an earlier draft completed it with a bracketed guess:

> `401/403 mean the API KEY is wrong; rotating the model cannot fix an auth`
> `misconfiguration and would silently destroy a working ensemble — so they are`
> `deliberately excluded.`

and `ROTATE_WORTHY_STATUSES`' own doc comment defines the criterion as statuses
meaning *"THIS MODEL ID is unusable — the only ones a model swap can actually
fix"*, dismissing everything else as *"an account, network, or provider problem
that rotation would not repair."*

**That criterion is exactly what this card's 403s satisfy — and the assumption
behind their exclusion is what fails here.** These 403s are **model-scoped**:
the account reaches all 15 other pool members and is refused only `inkling` /
`inkling-small`. A model swap *does* fix them. The exclusion is correct for the
account-wide 403 the authors had in mind, and wrong for this case, which they
did not. That is the defect, stated in the codebase's own terms.

**`ROTATE_WORTHY` gates real decisions, not just log text** (checked, because a
constant's membership list is not evidence of how it is consumed). Every
consumer read: `model-events.ts:362` sets
`persistentlyBroken = rotateWorthy && run >= minConsecutive`, and that flag
reaches two decision sites —

- `auto-replace.ts:528` — `brokenSlots` → `rotationNeeded`, which drives
  **ensemble slot replacement**;
- `index.ts:2276` — `runtimeUnavailableIds`, which authorizes a **paid
  benchmark** (*"A transient 429/502/503 blip must never authorize a paid
  benchmark"*).

So excluding 403 has teeth: a model failing 403 forever is never declared
`persistentlyBroken`, never auto-replaced, never counted runtime-unavailable.

**But note the scope, and do not over-read it:** both sites are about
**ensemble slots** (`model` / `second_model` / `third_model`) and paid-benchmark
authorization. This card's 403 members live in `free_models`, not in an ensemble
slot. **Whether this machinery reaches free-pool members at all is NOT
verified** — it may simply not be the relevant path.

**Explicitly NOT verified:** which of these paths a free-pool member's 403
actually takes at runtime. The `serviceLevel` consumers read here
(`:1743`, `:4695`, `:4825`) are file-processing paths; that a pool-rotation 403
reaches `classifyError` at all is **untraced**. Do not cite this section as
having established the runtime behavior — it establishes only what the code
says, at three sites, about 403 in general. Tracing the actual path is the
first task for whoever implements this card.

## 3d. Proposed fix shape — ADVISORY ONLY, NOT RATIFIED (2026-08-27)

From a Fable advisory consult. **Recorded, not adopted.** No approval has
been given; this section exists so the reasoning survives, not to authorise
work. Three earlier shapes died in §3b.1–3b.3, so a fourth gets written down
before it gets built, not after.

**The claim:** the permanent, model-scoped access fact already has a home —
`model-events.ts`'s persistence verdict. Its own documented criterion for
`ROTATE_WORTHY_STATUSES` is "THIS MODEL ID is unusable — the only ones a swap
can fix", which a model-scoped 403 satisfies. Only the constant's membership
disagrees with its own stated criterion.

**Why this survives invariant 2, where a denylist did not:** `filterFreeModels`
already hard-excludes `benchmarkFailed`, and reconcile already hard-drops dead
ids — so "never hard exclusion" is not a law of this codebase. The invariant's
real content is *never exclude unboundedly on a heuristic*. A 24 h-windowed
verdict self-heals: evicted → no calls → the run ages out of the window →
reconcile re-adopts → one re-probe per day. That is a probe-cadence change,
not an exclusion. **This is the load-bearing argument and it is the one to
attack first** if this shape is ever taken up.

**The trap, explicitly:** do NOT simply add 403 to `ROTATE_WORTHY_STATUSES`.
The same constant gates ensemble auto-replace and paid-benchmark
authorisation, so a genuinely account-wide bad key would 403 every model and
churn the entire pool. It needs a cross-model guard — isolated trailing-403
runs ⇒ model-scoped, act; ~all models with in-window events ⇒ account-scoped,
abstain — computable from the same events array.

**Plumbing note:** the broken set must enter `computeReconcile` in BOTH the
`kept` filter and the adoption filter, or a dropped model is re-adopted on the
next fire and oscillates.

**Named failure mode:** a spurious or temporary provider 403 evicts a healthy
model for ~24 h plus reconcile lag — bounded and self-healing. Cheapest early
signal that the guard has misfired: several members evicted in a single
reconcile fire, which means an account-scoped 403 leaked through. That should
log loudly and abort the write.

**Scope caution:** this touches `model-events.ts`, `model-reconcile.ts` and
`free-rotation.ts`, and changes a constant that gates paid-benchmark
authorisation. That is no longer the Tier-0 chore this card was opened as.

> 3. **NOT a live defect:** ordering has a floor — a pool of <=3 selects the

>    verdict, so the evidence fold is a no-op for this pool and ranking

§3a asked this and told whoever answered it to "investigate before writing
anything new". Answered here, by reading the code — not inferred. **Two
independent gaps. Neither is a bug in the ranking logic; both are gaps in
WHERE it is applied and WHAT it can see.**

### 3e.1 The evidence fold reaches selection at exactly ONE call site

`combinedFreeModelEvidence()` is consumed by ONE call —
`index.ts:2917-2922`, the `selectFreeEnsembleModels(...)` in
`getEnsembleModels`'s free branch. **Cite `index.ts:2921` when grepping for
the symbol**: `:2917` is the assignment line and does not contain the name.
Every other pool resolution calls bare `approvedFreePoolFromSettings()`
(`free-rotation.ts:394`), which applies `filterFreeModels` and **no
evidence at all**:

| call site | path | ranked |
|---|---|---|
| `index.ts:2921` | initial ensemble pick | yes |
| `free-rotation.ts:1127` | `withFreeRotation` rotation pool | **no** — see the hooks note below |
| `provider/completion.ts:949` | retry / fallback pool | **no** |
| `index.ts:963`, `index.ts:2019` | reconcile | **no** |

**Hooks note (the row's honest form).** `free-rotation.ts:1127` reads
`hooks.pool ?? approvedFreePoolFromSettings` — a DEFAULT, not a call, so
the unranked pool is only what runs when no caller injects one. Enumerated,
not assumed: `withFreeRotation` has exactly two non-test call sites,
`mass_scouting/cli.ts:502` and `security_scan/openrouter.ts:38`, and both
are `withFreeRotation(rawFetch)` with **no hooks argument at all**. So in
production the default is always what runs and the row stands; only tests
inject a pool.

So ranking gates ENTRY and rotation RE-ADMITS: when the first pick 429s and
rotation engages, the replacement is drawn from the unranked pool and a
just-demoted model can land in the slot ranking excluded it from. **This is
a mechanism argument derived from the call graph, NOT an observation** — no
run was watched re-admitting a demoted model. The tier is not wrong; it is
SILENT outside its one call site, because its scope is narrower than the
invariant it guards.

### 3e.2 The runtime strike is structurally blind to this failure

`recordNoContentStrike` has exactly two call sites
(`provider/completion.ts:1267` and `:1324`). `isEmpty` is
`resp.content.trim().length === 0` (`completion.ts:1179`). The `:1324` site
tests `isEmpty` directly; the `:1267` site does **not** name it — it tests
`useEmptyBudget`, which is `isEmpty && backend.type === "openrouter"`
(`completion.ts:1190`). So emptiness gates both, one directly and one
transitively — cite `:1190` for the second, not `:1179`. Because
`isEmpty === false` alone blocks both sites, the model's `finishReason` is
MOOT here and was never measured; no claim in this section depends on it.
`nemotron-3.5-content-safety` returned **17 content chars** on a 25k chunk
— not empty — so it accrues **zero strikes, ever**, and
`noContentDemotedModels()` can never demote it. The runtime half of the
evidence only sees "emitted nothing", never "emitted uselessly little".

**Root cause of the inert fold — checked, because a near-empty map is also

The write path is NOT missing — all six benchmarks set it

against the golden dataset. The rows on disk were written by the
requirements gate, which never scores. **`qualityPass` was added on

written one since.** The fold is therefore inert not by misdesign but for
want of a single $0 benchmark run over the free pool.

consequence-past-the-measurement.** `EVIDENCE_MAP_SIZE = 2` was consistent
with three different worlds — (i) the read failed, (ii) rows exist and are
correctly skipped, (iii) nothing was ever benchmarked — and the wording
picked (iii) with a bit of (i). The measurements above settle it on
**(ii)**, which is the module doing exactly what the 2026-08-05 fix built
it to do: refuse to let a class rejection masquerade as individual
evidence. The honest statement is: *no `:free` member has yet earned a
scored golden-dataset verdict, so the fold is a no-op for this pool BY
DESIGN until a bench run writes `qualityPass` rows.*

opposite direction.** Having wrongly called this a defect, the rewrite

